## 二、代码质量 & 架构

### 2.1 方法职责问题

#### `ShortLinkServiceImpl.restoreUrl` — 132 行 God Method

```
┌─────────────────────────────────────────────────┐
│ restoreUrl (132 lines, 7 个职责)                   │
│                                                 │
│ 1. L1 Caffeine 缓存查询                           │
│ 2. L2 Redis 查询 + L1 回填                       │
│ 3. 空值缓存检查 (is-null:goto_)                   │
│ 4. Bloom Filter 检查                             │
│ 5. L3 MySQL 查询 + 分布式锁 + 双重检查缓存回填       │
│ 6. 统计记录发送 (STATS_EXECUTOR.submit)            │
│ 7. sendRedirect + Cookie 写入                    │
└─────────────────────────────────────────────────┘
```

同一种 **"缓存命中→记录统计→重定向"** 的模式在方法内重复了 5 次（各行：424-429, 434-441, 478-489, 486-489, 531-534），每次只差缓存层级不同。

**建议**：抽取为模板方法模式或策略模式，每个缓存层一个 handler。

#### `ShortLinkStatsSaveConsumer.actualSaveShortLinkStats` — 75 行持有分布式锁做 9 件事

```
actualSaveShortLinkStats (75 lines, 持有 Redisson readLock):
  ├─ 1. 获取分布式 readLock
  ├─ 2. Redis SETNX UV 去重
  ├─ 3. Redis SETNX UIP 去重
  ├─ 4. 查库补全 gid
  ├─ 5. HTTP 调用高德 API (持有锁期间！)
  ├─ 6. ClickHouse 写入 (7 张表)
  ├─ 7. MySQL 写入 (8 张表)
  ├─ 8. Redis SCAN 批量失效缓存 (持有锁期间！)
  └─ 9. SSE 广播推送
```

**致命问题**：HTTP 调用（高德 API）在 `readLock` 内部。API 超时意味着集群中所有节点的 `updateShortLink` 的 writeLock 全部排队阻塞。

**建议**：将 IP 解析移到 Consumer 入口，锁仅保护缓存/DB 写入。对 8 张 MySQL 表 + 7 张 ClickHouse 表的插入使用批量策略或异步写入。

#### `ShortLinkStatsServiceImpl` — 400+ 行复制粘贴

`oneShortLinkStats`(209 行) 和 `groupShortLinkStats`(228 行) 逻辑几乎完全相同，仅仅是 mapper 不同。这是全项目最大的代码重复。

### 2.2 @Transactional 边界问题

```
┌──────────────────────────────────────────┐
│ createShortLink (line 114)               │
│   @Transactional                         │
│                                          │
│  DB insert ✓                             │
│  Redis set → 不在 Spring 事务管理器内     │
│  Bloom filter add → 同上                 │
│  Favicon HTTP → STATS_EXECUTOR 异步       │
│                                          │
│  结论：DB 可能提交成功，Redis 可能写入失败  │
│       → 缓存不一致                        │
└──────────────────────────────────────────┘

┌──────────────────────────────────────────┐
│ updateShortLink (line 275)               │
│   @Transactional                         │
│                                          │
│  cross-group 分支：                       │
│  → 在 @Transactional 内获取分布式写锁     │
│  → 持有 DB 连接期间等待分布锁             │
│  → 浪费连接池                             │
│  → finally 释放锁后，缓存失效不再受保护    │
└──────────────────────────────────────────┘
```

**建议**：分布式锁应该在 `@Transactional` 外部获取，先锁再开事务。Redis/Bloom 操作应该在事务提交后执行（使用 `TransactionSynchronization`）。

### 2.3 线程池 "静默丢数据"

项目中有 3 个 static 线程池：

| 线程池 | 拒绝策略 | 队列 | 风险 |
|--------|---------|------|------|
| `STATS_EXECUTOR` | `DiscardPolicy` | ArrayBlockingQueue(2000) | 高峰期统计任务静默丢弃 |
| `MONITOR_EXECUTOR` | `DiscardPolicy` | LinkedBlockingQueue(1000) | 监控指标静默丢失，daemon 线程被杀时 pending 任务丢失 |
| `STATS_QUERY_EXECUTOR` | `CallerRunsPolicy` ✓ | LinkedBlockingQueue(500) | 唯一正确的，但队列偏小 |

5,000 QPS (Sentinel 限制) 下，2000 容量的队列 + DiscardPolicy → 超过队列上限的请求的统计数据全部静默丢失，无任何告警或日志。

**建议**：
- 统计类任务改用 `CallerRunsPolicy` 提供背压
- 添加 `RejectedExecutionHandler` 的自定义实现，至少记录日志和 metrics 计数
- 所有 `static final` 线程池添加 `@PreDestroy` 的 `shutdown()`

### 2.4 MQ 消息丢失链路

```java
// ShortLinkStatsSaveProducer.java:45
rocketMQTemplate.asyncSend(topic, build, new SendCallback() {
    public void onException(Throwable ex) {
        log.error("...", ex);  // 仅记日志，无重试，无死信队列
    }
}, 2000L);

// 调用方 (ShortLinkServiceImpl.java):
shortLinkStatsSaveProducer.send(producerMap);
// 不检查返回值，不处理失败
```

**完整丢失链路**：`STATS_EXECUTOR` DiscardPolicy 丢弃 → 即使提交成功，MQ asyncSend 失败 → 仅日志记录。两个环节都无兜底。

**建议**：加上 RocketMQ 重试机制 + 死信队列，或至少落库做异步补偿。

## 三、可观测性

### 3.1 致命问题：Prometheus 指标"名存实亡"

`docs/observability.md` 文档中声称的 8 个指标族：

| 文档声称的指标 | 实际实现 |
|---------------|---------|
| `shortlink_redirect_total` (Counter) | **不存在** — 实际用 `AtomicLong` |
| `shortlink_cache_hit_total` (Counter) | **不存在** — 实际用 `AtomicLong` |
| `shortlink_redirect_duration_seconds` (Histogram) | **不存在** |
| `shortlink_errors_total` (Counter) | **不存在** |
| 及其余 4 个指标族 | **不存在** |

`PerformanceCounterServiceImpl` 中使用的是普通 `AtomicLong`，这些计数器根本没有注册到 Micrometer MeterRegistry，Prometheus endpoint (`/actuator/prometheus`) 不会输出它们。

### 3.2 高危问题

| # | 问题 | 影响 |
|---|------|------|
| 33 | **无 `logback-spring.xml`** — 日志格式、级别、滚动策略全靠 Spring Boot 默认值，生产排查困难 | 多行日志（如异常堆栈）无结构化，无法被日志聚合系统正确解析 |
| 34 | **无分布式追踪 (OpenTelemetry)** — 没有 TraceId 注入，无法跨服务追踪一次完整请求链路 | 排查跨服务问题时只能凭时间戳猜测 |
| 35 | **无自定义 HealthIndicator** — Redis/ClickHouse/RocketMQ 存活状态不反映在 `/actuator/health` | 即使这些中间件挂了，health check 仍返回 UP |
| 36 | **Docker healthcheck 只是 TCP 端口检查** — `bash -c '</dev/tcp/127.0.0.1/8001'` 不校验应用实际健康 | 端口在但应用 hung 住时不会自动重启 |
