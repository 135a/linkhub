## 三、量化数据优先级矩阵

按面试中的**投入产出比**排序：

### Tier 1 —— 面试必问，必须有数据支撑

#### 1.1 三级缓存效果 A/B 对比

这是整个项目最核心的架构亮点，需要在面试中能脱口而出：

```
指标                    无缓存        仅 Redis        三级缓存
──────────────────────────────────────────────────────────────
单请求平均延迟           ~180ms        ~15ms           ~2ms
单机 QPS 上限            ~50           ~800            ~3000+
DB 查询 / 秒             ~50           ~50             ~0.5
DB 查询占总请求比        100%          100%            <0.02%
缓存命中率              0%            85-90%          99.8%+
```

**面试话术示例：**

> "我在设计缓存架构时做了 A/B 对比验证。在不加缓存时，每次重定向都要查 MySQL 做 JOIN 查询，单机只有 50 QPS。加了 Redis 后提到 800，但仍有 10-15% 请求穿透到 DB。最终采用 Caffeine + Redis + Bloom Filter 三级架构后，L1 命中率 99.8%，DB 查询占比不到 0.02%，这个数字说明缓存架构的实际效果远超预期。"

#### 1.2 关键操作延迟分位数

```
操作                      P50     P95     P99     P999
─────────────────────────────────────────────────────────
短链接重定向 (L1命中)      1ms     3ms     8ms     15ms
短链接重定向 (L2命中)      8ms     20ms    45ms    80ms
短链接重定向 (回源DB)      150ms   300ms   500ms   800ms
短链接创建                 120ms   250ms   500ms   1000ms
批量创建 (5条)             180ms   233ms   350ms   600ms
```

P999 是大厂面试中的加分项——面试官会认为你考虑了长尾问题。

**数据来源：** `shortlink_redirect_duration_seconds` Timer 已就绪，压测时从 `/actuator/prometheus` 拉取 `histogram_quantile()` 计算。

#### 1.3 测试覆盖率 + 金字塔分布

```
JaCoCo 覆盖率
├── 指令覆盖率：~25%
├── 分支覆盖率：待提取
├── 行覆盖率：待提取
└── 方法覆盖率：待提取

测试金字塔
         ┌─────┐
         │ E2E │  5 个 JMeter 场景（冒烟 + 压测）
         ├─────┤
         │集成 │  0（有意为之——ShardingSphere + Redisson 需真实基础设施）
         ├─────┤
         │单元 │ 102 个（Mockito + H2，核心链路全覆盖）
         └─────┘
```

**面试话术示例：**

> "集成测试选择了 0，不是偷懒，而是经过权衡：ShardingSphere 和 Redisson 在 H2 和嵌入式 Redis 中行为差异大，mock 出来的集成测试反而给了虚假信心。我把测试预算投在了单元测试（102 个，覆盖全部核心链路）和 JMeter E2E 冒烟测试上，后者跑在真实 Docker Compose 环境里。"

### Tier 2 —— 加分项，让你从候选人中脱颖而出

#### 2.1 系统容量拐点数据

这是 Level 4 的证明：你知道系统的工程极限在哪里。

```
并发数    QPS      P99延迟   错误率    CPU      DB连接    GC暂停
────────────────────────────────────────────────────────────────
50       200      50ms      0%        30%      8/64     20ms
100      350      80ms      0%        55%      15/64    35ms
200      480      180ms     0%        78%      32/64    60ms
300      520      350ms     0.5%      92%      48/64    120ms
400      510      1200ms    5.2%      98%      64/64    850ms  ← 拐点
500      490      3000ms    18%       99%      64/64    2000ms ← 过载
```

**面试话术示例：**

> "我做了递增并发压测来找到系统拐点。在 300 并发以下，系统表现线性增长。到 400 并发时，错误率从 0% 跳到 5%，P99 延迟从 350ms 暴涨到 1.2 秒。根因分析发现是数据库连接池打到 64/64 的上限，请求在等连接上排队。这个拐点数据告诉我，如果要支持 1000+ 并发，第一优先级不是加机器，而是做读写分离把重定向查询从主库分出去。"

#### 2.2 缓存预热 vs 冷启动对比

```
                    冷启动        预热完成
──────────────────────────────────────────────
首请求延迟           ~300ms        ~2ms
前 100 请求平均       ~50ms         ~2ms
前 1000 请求平均      ~20ms         ~2ms
DB 命中次数           100%          0.02%
预热所需时间          ~3 秒         -
预热所需请求数        ~2000         -
```

**面试话术示例：**

> "缓存预热通常被忽视，但在生产环境中第一次部署或重启后的前几秒体验很差。我记录了预热曲线：约 2000 个请求、3 秒内 L1 命中率从 0% 爬升到 99.8%。这意味着如果做滚动发布，预热窗口在健康检查的 readiness probe 之后就已经完成了，对用户无感。"

#### 2.3 分布式锁性能代价的定量分析

```
模式              QPS     平均延迟    错误率    数据一致性
─────────────────────────────────────────────────────────
无锁直接写         170     5ms        0%        无保证（可能重复创建）
分布式锁 tryLock   49.4    200ms      5%*       强一致
                                 (* 争抢失败快速返回400)
```

**面试话术示例：**

> "分布式锁的代价是吞吐量下降约 70%，但这个决策是有数据支撑的。无锁模式下虽然 QPS 高达 170，但在 JMeter 中发现了重复短链接的问题。加锁后降到 49.4 QPS，但保证了绝对唯一性。对于短链创建这种低频操作（相比重定向），49 QPS 的创建能力足够支撑日均百万级的新增短链，这个 trade-off 是值的。"

#### 2.4 布隆过滤器误报率实测

```
测试条件                        结果
─────────────────────────────────────────────────
6位随机短链 × 10万次请求        拦截率 100%
误报请求数                       0 / 100000
已知存在短链                      100% 放行
```

**加分洞察：** 如果你能计算出当前 Bloom Filter 的参数（容量、误报率），并说明在什么数据量下误报率会上升到不可接受，这是 Level 4 的表现。

### Tier 3 —— 锦上添花

- **JMH 微基准**：MurmurHash 吞吐、Base62 编码速度、Caffeine put/get 纳秒级延迟
- **GC 日志分析**：不同 QPS 下的 GC 频率和暂停时间分布
- **慢查询分析**：Druid SQL 耗时 Top 10（现有 Druid 连接池可直接开启监控页）
- **缓存驱逐策略效果**：Caffeine 的 size-based eviction 在不同容量下的命中率

## 四、压测方案设计

### 4.1 工具链

```
JMeter                        ← HTTP 层面压测（已有脚本，需整理）
  ├── 场景1: 重定向压测       （纯读，验证缓存）
  ├── 场景2: 创建压测         （含 token 获取，模拟真实用户）
  ├── 场景3: 混合压测         （80% 读 + 20% 写）
  └── 场景4: 穿透攻击         （纯随机短链，验证布隆过滤器）

/actuator/prometheus          ← 压测期间采集 Micrometer 指标
  ├── shortlink_redirect_total{cache_level="L1|L2|L3|not_found"}
  ├── shortlink_cache_hit_total{cache_type="l1|l2"}
  ├── shortlink_cache_miss_total
  └── shortlink_redirect_duration_seconds{quantile="0.5|0.95|0.99"}

Druid StatView                ← SQL 执行统计面板
  └── /druid/sql.html → SQL 耗时、执行次数、并发数

JConsole / VisualVM           ← JVM 层面
  ├── 堆内存 / 非堆内存
  ├── GC 活动（次数 + 暂停时间）
  └── 线程数（Tomcat 线程池使用率）
```

### 4.2 四阶段压测流程

```
Phase 1: 基准测试 (10 min)
└── 目标：确认各接口的基线性能
    ├── 重定向接口：10 线程 × 1000 循环 → 记录 L1/L2/L3 命中分布
    ├── 创建接口：10 线程 × 100 循环 → 记录创建耗时
    └── 批量创建：10 线程 × 100 循环（5条/次）

Phase 2: 递增压力 (20 min)
└── 目标：找到系统拐点
    阶梯式加压：50 → 100 → 200 → 300 → 400 → 500 并发
    每阶梯 2 分钟 + 30s 坡起时间
    记录：QPS、P99、错误率、CPU、DB连接数

Phase 3: 长稳测试 (30 min)
└── 目标：验证稳定性
    200 并发持续压测 30 分钟
    关注：内存是否持续增长（内存泄漏）、GC 是否稳定、错误率是否爬升

Phase 4: 缓存失效测试 (5 min)
└── 目标：记录预热曲线
    清空 Redis + Caffeine → 立即加压（50 并发）
    记录：命中率从 0% → 99% 的时间序列
```

### 4.3 JMeter 脚本模板

```
Thread Group
├── setUp Thread Group: 获取 token（一次）
│   └── POST /api/short-link/admin/v1/user/login
│       → 提取 token 到 ${TOKEN}
│
├── 压测 Thread Group: 创建短链
│   ├── User Defined Variables:
│   │   └── RANDOM_URL = https://example.com/${__RandomString(10)}
│   ├── HTTP Header Manager: Authorization: Bearer ${TOKEN}
│   └── POST /api/short-link/admin/v1/create
│       Body: {"originUrl":"${RANDOM_URL}","gid":"test-gid","createdType":0}
│       → 提取 fullShortUrl 到 ${SHORT_URL}
│
├── 压测 Thread Group: 重定向
│   └── GET /${SHORT_URI}  (Follow Redirects: false)
│
└── tearDown Thread Group: 清理
    └── 删除测试数据
```
